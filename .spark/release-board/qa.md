## 3. Exploratory Findings

| # | Severity | Steps to reproduce | Expected vs. observed | Status |
|---|---|---|---|---|
| B1 | **Major** | Two independent repros, both real `git init`/`commit`/`tag`, no mocking: **(a) deleted/renamed feature directory** — `cd` into a fresh repo; commit `.spark/oldfeature/spec.md`, `git tag v1.0.0`; then `git rm -r .spark/oldfeature`, add `.spark/newfeature/`, `git tag v2.0.0`; run `insights releases --as-of <date> --repo .`. **(b) tag on an unreachable branch** — commit A on `main`, tag `v1.0.0`; branch `side` off A, commit B adding `.spark/feat_b/spec.md`, tag `v2.0.0` on B; back on `main`, commit C adding `.spark/feat_c/` (not descended from B); run `insights releases` while checked out on `main`. | **Expected** (per AC-1.2/A7: membership decided by "does `git log <range> -- .spark/<feature>/` return ≥1 commit"): `v1.0.0`'s own member list includes `oldfeature` (repro a); `v2.0.0`'s member list includes `feat_b` (repro b) — independently confirmed via plain `git log v1.0.0 -- .spark/oldfeature/` and `git log v1.0.0..v2.0.0 -- .spark/feat_b/`, both of which return the commit. **Observed:** in both repros the commit that unambiguously touched the feature's own `.spark/<feature>/` path is instead dumped into `unattributed`, and the feature never appears as a member of *any* release — not even the one it was tagged under. Root cause: the feature-directory candidate list is built once from `Path.iterdir()` on the **current working tree's** `.spark/` (per plan T2's own DoD), not per-range from git history — so any feature directory absent from *whatever's currently checked out* silently loses all its historical membership and its commits get reclassified as anonymous "unattributed" noise, with no error, warning, or `reason` field disclosing why. This is exactly the class of silent-wrong-answer this feature exists to prevent (A7/AC-1.3's "never dropped, never guessed" promise), just triggered from the opposite direction: a commit *does* touch a real `.spark/<feature>/` path but is bucketed as if it touched none. Does not currently manifest on the real target repo (no `.spark/<feature>/` dir has ever been renamed/deleted there, and all 5 tags sit on linear `main` history) — but neither renaming/retiring a feature directory nor tagging off a non-`main` branch is forbidden by this spec, and this project's own `insights board` already treats multiple local branches as a first-class concept, so the precondition is realistic, not exotic. **Fixed:** the candidate feature-name set was widened from "current working tree only" to the union of (a) the current checkout (`_list_feature_dirs`, unchanged) and (b) every `.spark/<name>/` path ever touched by a commit reachable from **any** ref (new `gitread.list_ever_touched_spark_feature_names`, one `git log --all --name-only -- .spark/` call), each name individually validated (NFR-2) regardless of source. The existing `git log <range> -- .spark/<name>/` membership check (T3/A7) already scored historical existence correctly — only the candidate list feeding it was scoped too narrowly. Re-ran both original repro commands verbatim after the fix: repro (a) — `v1.0.0`'s member list is now exactly `["oldfeature"]`; repro (b)'s underlying mechanism (a tag on a non-current branch) verified via a from-scratch `side`-branch fixture — `feat_b` now correctly appears as `v2.0.0`'s member while `main` stays checked out. Real target repo output confirmed byte-identical before and after the fix (no directory there has ever been renamed, so nothing was expected to change). Two new regression tests: `test_a_deleted_feature_directory_still_appears_in_the_release_it_shipped_in`, `test_a_feature_only_reachable_via_a_tag_on_another_branch_still_appears` (`tests/test_releasemap_membership.py`). Recorded as a plan deviation (`.spark/release-board/plan.md`, "Deviations" section) — small, obvious correction within the existing architecture, no `/sprint-plan` revision needed. | **verified** — independent re-test, see below |
